events (1,476 exact redeliveries). Each check compares a target with an oracle written in plain

## Quality control (DMAIC)

### Define

See [RFC 0001](../rfc/0001-design.md): reruns and crashes must leave 0 duplicate rows, 0 gaps, 0
partially visible partitions, a ledger that matches the data in every crash scenario, reruns of
unchanged input that change 0 rows (merge and dedup), and unsafe input rejected before commit.

### Measure: the baseline

The two anti-patterns on copies of the demo targets, same source, both engines (`Bench.baseline`):

| Anti-pattern | DuckDB | SQLite |
|---|---|---|
| Plain `INSERT ... SELECT` run twice over 30 days | 62,952 rows for 30,000 events: 32,952 duplicates (1,476 redeliveries from the first run plus 31,476 from the rerun) | the same: 32,952 duplicates |
| `DELETE` and `INSERT` committed separately, crash between them on 2026-01-16 | 5 rows of that day missing (a gap) | 5 missing |

### Analyze

- **The baseline defects come from the write, not the data.** Appends have no notion of "already
  written", and redeliveries in the source add duplicates even on the first run. The overwrite
  gap is the window between two commits.
- **A defect found in the first implementation: DuckDB unique indexes after an unclean exit.**
  The CLI crash test (kill, separate `verify` process, rerun) ended with 120 rows in `dim_orders`
  for 78 orders: 42 duplicates. Root cause, isolated with `scripts/duckdb_index_after_unclean_exit.py`
  (output below): in DuckDB 1.5.6, rows committed only to the write-ahead log when the process
  dies are missing from the unique index after the next open replays the log and checkpoints. A
  duplicate key is then accepted, and `MERGE`, which used the index to find matches, inserts a
  second row instead of updating. The in-process bench had not caught it because it reopened
  without an intermediate close (no checkpoint before the rerun).

  ```
  duckdb 1.5.6
  unclean exit, rows only in the WAL
    duplicate key 'a': accepted
    rows after MERGE of ('b', 5): [('a', 1), ('a', 9), ('b', 1), ('b', 5)]
  control: CHECKPOINT first
    duplicate key 'a': rejected
    rows after MERGE of ('b', 5): [('a', 1), ('b', 5)]
  ```

- **SQLite overwrite is slower** (3.4 s versus 0.6 s for 30 partitions): the plan shows SQLite
  does not push the partition filter through the demo view's two aggregation levels, so every
  partition read scans the whole source. It affects the demo view, not correctness.
- **Bulk loading on DuckDB:** binding 31,476 rows as parameters took 130 s (multi-row `VALUES`)
  and 150 s (`unnest` of lists); writing a private CSV and `read_csv` took 0.2 s, now used by
  `bulk_insert` on DuckDB.

### Improve

| Change | Effect |
|---|---|
| The three patterns and the ledger in one transaction per partition (ADRs 0002, 0003) | Baseline 32,952 duplicates and 5 missing rows per engine to 0 and 0 in all 82 scenarios |
| No unique indexes on DuckDB; post-write check of touched keys on both engines (ADR 0004) | The kill, separate open, rerun sequence: 42 duplicates to 0. With the indexes switched back on, the check alone stops the rerun (`DuplicateKeyError`, 25 keys) instead of committing duplicates |
| Tests and bench close and reopen the file between a kill and the rerun | The sequence that exposed the DuckDB behaviour is now part of the crash matrix |
| CSV staging for DuckDB `bulk_insert` | Loading the 31,476-row source: 130 s to 0.3 s |
| Bench reads the source once per engine instead of per check | Bench time 116 s to 108 s (before the index change; 97 s for the final run) |

### Control

- **CI gates** (`.github/workflows/ci.yml`): install from `constraints.txt`; `make lint` (ruff,
  ruff format, mypy `--strict`); all 182 tests with the summary as a `::notice`; `ibk bench` with
  its `RESULT` line as a `::notice` and the table in the job summary (the bench exits 1 if any
  pattern scenario has a defect or the baseline stops showing one); `make repro` (informational);
  pip-audit. Failing output is posted as an `::error` annotation.
- **Mistake-proofing in the code:** identifiers validated against a strict pattern and quoted,
  every value bound as a parameter; specs that cannot be run safely (merge without a version,
  overwrite with a key, reserved names) are refused at construction; partitions must be calendar
  dates; NULL keys and conflicting content stop a partition before it writes; overwrite refuses
  to empty a partition; the post-write key check makes a committed duplicate impossible; a ledger
  row cannot be written outside the data's transaction; job files have exact keys and a size cap.
